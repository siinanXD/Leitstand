# SIN-553: Vorarbeiter plant die Reihenfolge und lässt so viel wie möglich parallel bauen

- Der CEO ([SIN-542](SIN-542-ceo.md)) entscheidet was, der Vorarbeiter wann und womit. Reine Planung in `src/lib/vorarbeiter/vorarbeiter.ts` (getestet, Fixture mit 8 Issues), Netz in `scripts/vorarbeiter/vorarbeiter.ts`. Der Issue nennt `scripts/autonomy/vorarbeiter.mjs`; dieses Repo hat Skripte je Agent in TypeScript (`scripts/ceo/`, `scripts/anwalt/`), deshalb gleiche Form.
- **Plan:** Startbar ist ein Issue im Status Todo mit Label `claude`, ohne `sinan`, `needs-human`, `design`. Berührte Stellen = Pfade aus dem Issue-Text (`src/…`, `scripts/…`, `docs/…`), ohne Pfade ersatzweise das Label `bereich:<name>`, ohne beides frei. Zwei Issues sind parallel, wenn sie keine Stelle teilen (Pfad gleich oder Ober-/Unterordner) und keiner den anderen blockiert.
- **Platzierung:** Blocker zuerst, dann in dessen Spur. Teilt ein Issue Stellen mit genau einer Spur, folgt es dort. Mit zwei Spuren: es wartet bis nach dem nächsten Merge (der Vorarbeiter läuft dann neu). Teilt es Stellen mit einem Issue, das schon läuft: wartet. Sonst die kürzere Max-Spur, oder Spur C, wenn es dafür taugt.
- **Reihenfolge:** Label `readiness` (bringt die Fertig-Liste voran) vor `dringend` (Priorität 1 oder Label) vor dem Rest nach Priorität und Alter. `docs/product-readiness.json` gibt es noch nicht, deshalb steht die Fertig-Liste als Label am Issue.
- **Loop-Infra** (`.github/`, `scripts/loop|waechter|vorarbeiter`, `src/lib/loop|waechter`, Label `loop`) wird nur mit dem Label `ceo-freigabe` eingeplant, sonst steht sie unter „wartet“.
- **Spuren:** A und B = Claude Max (wie heute, der Dispatcher startet sie weiter über `loop.ts`; der Plan ordnet an, er ersetzt den Dispatcher noch nicht). C = API mit `claude-haiku-5-5`.
- **Spur C:** Nur Issues mit Label `groesse:klein`, deren genannte Pfade alle unter `docs/` liegen (`groessen.md` gibt es nicht, das Label ersetzt die Schätzung). Tests und Code laufen nicht über C, weil dort niemand `npm test` ausführt. Die Modellantwort ist eine Vertrauensgrenze: nur Markdown unter `docs/`, nur Pfade aus dem Issue, höchstens 5 Dateien, alles oder nichts. Dann Branch `claude/sin-N-c`, Commit je Datei, PR (kein Draft, kein Merge durch den Vorarbeiter). Das Linear-Issue springt auf „In Progress“, damit der Dispatcher es nicht doppelt startet.
- **Kosten:** Preise (`VORARBEITER_PREIS_EIN_USD`, `VORARBEITER_PREIS_AUS_USD`, USD je Million Token) und `KOSTEN_USD_EUR` kommen aus der Umgebung, nichts ist fest eingebaut. Fehlt eins, wird Spur C nicht gebaut. Die Kosten gehen vor der Prüfung der Antwort als Zeile `{cost_eur}` in `pipeline_run_costs`. Tagesdeckel 2 €: gezählt wird die ganze Tagessumme des Ledgers (UTC-Tag), also eher zu streng. Annahme wie in [SIN-527](SIN-527-kosten.md): die Spalte `cost_eur` genügt, `created_at` setzt die Datenbank; weicht das Schema ab, nur `ledgerZeile` anpassen.
- **Speicherort:** `loop_snapshot.plan` (jsonb) gibt es noch nicht. Migration als `docs/autonomy/loop_snapshot_plan.sql.vorlage`, nicht unter `supabase/migrations/`, damit sie nicht mit diesem PR live geht. Der Leitstand liest `plan` optional; ohne Spalte oder ohne Plan fehlt der Block auf der Ablauf-Seite.
- **Ablauf-Seite:** Block „Spuren des Vorarbeiters“ mit den drei Spuren: was läuft (Issue in Arbeit laut Snapshot) und was als Nächstes kommt, darunter was wartet und warum. Die Bahnen sind eine Liste im bestehenden Stil, noch kein Figma-Frame dafür (Design-Label wäre nötig).
